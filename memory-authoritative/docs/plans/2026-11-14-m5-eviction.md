# M5: Eviction — Idle Sweep, Capacity Eviction, the Dead Protocol — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Memory holds only the working set. Clean entries that sit idle longer than `IdleTTL` are removed from memory, and tombstones and negative-cache entries go after `NegativeIdleTTL`. Least-recently-accessed entries are removed when the table exceeds `MaxEntries`. An access during or after a removal is just a miss that reloads the same state (design.md 7.7).

**Architecture:**
- Each entry gets `dead` and `lastAccess`; the Store gets `nowSec`, `entryCount` and a background evictor.
- `tryEvict` runs the dead protocol:
  1. take `op` with `tryLockOp`;
  2. under `mu`, re-check that the entry is still evictable (`!dead`, `dirty == 0`, and the policy's `eligible`), then set `dead`;
  3. release `mu`, then delete the entry from the map under `shard.mu`.
- Every lock taker checks `dead` and starts over. Lock-free readers do not.
- The idle sweep and capacity eviction sample K entries per shard under `RLock`, release it, then call `tryEvict`.
- The first store failpoints, on one mechanism, reach the two gaps that are not DB calls.

**Tech Stack:** Go 1.25 (`testing/synctest`), standard library; Porcupine (tests, from M4).

### Decisions in this plan that the design does not fix

1. **The failpoint mechanism.** It is one optional field, `Store.failpoint func(at string, e *entry)`, which is nil in production and set only by tests in the package. It is called through `s.fail(at, e)`, which does nothing when the field is nil. M5 has two points:
   - `"evict-sample"`: after a sweep has taken its sample and released `RLock`, before it calls `tryEvict`;
   - `"evict-dead"`: after `tryEvict` has set `dead` and released `mu`, before it takes `shard.mu`.

   These are the gaps of tla-mapping 3.1 that are not DB calls; `fakedb.Hook` keeps the DB ones. This is the "one mechanism" of CLAUDE.md.
2. **The clock and the evictor run in one goroutine,** `RunEvictor(ctx)`, which the caller starts, as with `RunFlusher`. It stores `time.Now().Unix()` into `nowSec` every second and runs one round every `EvictInterval`: the idle sweep of every shard, then capacity eviction if needed. `New` initializes `nowSec`.
3. **Config values, where 11.4 leaves them open:**

   | Setting | Default | Allowed |
   |---|---|---|
   | `IdleTTL` | 10min (11.4: TBD) | ≥ 0 |
   | `NegativeIdleTTL` | 1min (11.4: 1–5 min) | ≥ 0 |
   | `EvictInterval` | 1s | > 0 |
   | `MaxSweepRounds` | 16 | > 0 |
   | `MaxEntries` | 1,000,000 (11.4: TBD) | > 0 |

   TTLs are compared in whole seconds: `int64(ttl / time.Second)`. A TTL of 0 means "not accessed during the current second", which is what the tests use to evict aggressively.
4. **Capacity eviction runs only when `entryCount > MaxEntries`.** It evicts down to the low-water mark `MaxEntries * 9 / 10`. Each shard gets an equal share of the excess, rounded up. For each shard:
   - repeat at most `MaxSweepRounds` times: take a sample of up to `sampleK = 64` entries, sort it by `lastAccess`, oldest first, and `tryEvict` each one with `eligible` returning true, until the share is met;
   - stop early when a whole sample evicts nothing, for example because everything in it is dirty. Backpressure for that case is M6.
5. **`touch` calls**, as in the design:
   - Get and Update, on every access;
   - Create and Delete, at the end, after the linearization point. For Delete this means the tombstone's `NegativeIdleTTL` counts from the delete.
   - `getOrCreate` sets `lastAccess` on a new entry.
6. **Until M5, Create and Delete used `getOrCreate` + `lockOp`.** They now use the design's `lockOpLive`, which loops until the entry it got is not dead. `load` checks `dead` after taking `op`, and returns nil so that the caller looks the key up again. `flushShard` treats a dead entry as nothing to write. Update, finding `dead` under `mu`, unlocks, calls `runtime.Gosched()` and starts over.
7. **Eviction in the randomized tests.** `TestStressCreateDelete` and `TestLinearizable` run `RunEvictor` with `IdleTTL 0`, `NegativeIdleTTL 0` and `EvictInterval 1ms`, and each worker waits 0–20ms of virtual time between operations, so that many second boundaries pass and eviction interleaves with every operation. In `TestLinearizable`, reloads now read the DB, so Porcupine also checks that a clean row in memory equals the DB (I4).

   The M2 `TestStressUpdates` runs on real time and stays without eviction.
8. **Witnesses (tla-mapping 8).**
   - `W_Evict` is counted by the tests through the `"evict-dead"` failpoint.
   - `W_Reload` is counted by `faults`, which now counts Select statements per key: a key that was selected more than once after an eviction.

   Both must be above zero in the two randomized tests.

## Review Focus

1. **A load that fails leaves `snap` nil.** Such an entry must be evicted after `NegativeIdleTTL`, and the next Get must load again rather than keep returning the cached error. Test: `TestFailedLoadEntryIsEvicted` (Task 2).
2. **A dirty entry is never evicted,** however long it is idle and however far the table is over `MaxEntries`. It is evicted once flushed. Test: `TestDirtyEntryNotEvicted` (Task 2).
3. **Capacity eviction when every sampled entry is dirty** must return without spinning, and keep the entries. Test: `TestCapacityEvictionAllDirtyReturns` (Task 2).
4. **An Update that meets an entry between `dead` and the map delete** must not be lost. After the removal it lands on a fresh entry loaded from the DB. Test: `TestUpdateDuringEvictionIsKept` (Task 1).
5. **A create retried with the same gen, after its tombstone was evicted,** must still answer `(nil, nil)` and not insert the row again. That is hole 2 with eviction between the delete and the retry: the load now reads absent from the DB, and the dedup table must still block it. Test: `TestRetryAfterTombstoneEvicted` (Task 2).
